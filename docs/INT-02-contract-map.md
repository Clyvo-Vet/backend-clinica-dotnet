# INT-02 — Mapa de contratos: mobile-clinica-rn ↔ .NET ↔ Luna

> TASK-09. Gerado validando cada chamada real de `mobile-clinica-rn/src/services/*.ts` contra os
> controllers .NET reais e o endpoint `/whatsapp/enviar` da Luna, rodando `.NET` contra um Oracle
> XE local (`DevOps-Cloud/docker-compose.yml`) via `scripts/test-e2e-clinica.sh`. Todas as
> divergências abaixo foram reproduzidas ao vivo, não deduzidas por leitura de código.

## Blockers de infraestrutura corrigidos nesta task

O smoke test só chegou a rodar depois de dois achados sérios, ambos aprovados via checkpoint antes
de qualquer alteração (ver decisão registrada na sessão):

### 1. Schema drift sistêmico .NET ↔ Flyway (CRÍTICO — corrigido)

O .NET (EF Core) tem 9 migrations "evidência" nunca aplicadas em produção por design (Flyway é a
única autoridade de DDL — CLAUDE.md). Na prática, várias dessas mudanças nunca foram espelhadas em
Flyway, deixando a maior parte da superfície clínica/IoT/notificação do .NET **inutilizável** contra
o schema real (`ORA-00904`/`ORA-00942` em qualquer request que tocasse essas tabelas/colunas):

- **11 tabelas inteiras ausentes**: `NOTIFICACAO`, `EXAME`, `VACINA`, `PRESCRICAO`, `DOCUMENTO`,
  `CONSULTA`, `MEDICAMENTO`, `TRIAGEM_LUNA`, `DISPOSITIVO_IOT`, `LEITURA_TEMPERATURA`,
  `ALERTA_TEMPERATURA`.
- **`EVENTO_CLINICO`** existia só como stub (V1, comentário: "suportar FK de AGENDAMENTO") —
  faltavam `ID_CLINICA`, `ID_VETERINARIO`, `ID_TIPO_EVENTO`, `DS_OBSERVACAO`, `DT_CRIACAO`,
  `DT_ATUALIZACAO` — as colunas que `CONSULTA`/`EXAME`/`VACINA`/`PRESCRICAO`/`DOCUMENTO` referenciam.
- Colunas de auditoria (`DT_CRIACAO`/`DT_ATUALIZACAO`) faltando em `VETERINARIO`, `ESPECIE`, `RACA`,
  `TIPO_EVENTO`, `INVITE_TUTOR`.
- `TIPO_EVENTO` também não tinha `CD_TIPO` (chave de negócio usada pelo .NET).
- `CLINICA.NM_RAZAO_SOCIAL` — descoberto isoladamente primeiro (bloqueava `POST /register-clinica`).

**Fix**: `V8__clinica_razao_social.sql` (o achado inicial) + `V9__schema_drift_clinico.sql`
(comprehensive — as 11 tabelas + colunas do `EVENTO_CLINICO` e demais tabelas), ambos no
`backend-tutor-java`. `EVENTO_CLINICO` tinha 0 linhas nesta base — `NOT NULL` direto, sem backfill.
`TIPO_EVENTO` tinha 3 linhas — `CD_TIPO` nasceu nullable, backfillado de `NM_TIPO` (já estava no
formato de código: `CONSULTA`/`TELEORIENTACAO`/`VACINA`), só então `NOT NULL + UNIQUE`. Validado que
V8/V9 aplicam igual em H2 (dev) e Oracle (prod) — precisou também corrigir
`db/callback/afterMigrate__seeds_dev.sql` (seed de `TIPO_EVENTO` não populava `CD_TIPO`, quebrando
o boot do profile `dev` depois de V9 tornar a coluna `NOT NULL`). Suite Java: 133/133 verde depois.

### 2. `LUNA_INBOUND_API_KEY` nunca chegava à Luna (corrigido)

`POST /whatsapp/enviar` (TASK-06) valida o header `X-API-Key` contra `settings.LUNA_INBOUND_API_KEY`
— mas essa variável nunca foi adicionada ao `DevOps-Cloud/docker-compose.yml` nem a nenhum
`.env.example`. Com o default `""` do Pydantic Settings, `not chave_esperada` é sempre `True` →
**o endpoint rejeitava 100% das chamadas com 401**, mesmo com a chave certa configurada no cliente
(porque não havia chave certa nenhuma — o servidor nunca recebia o valor). Fix: adicionado
`LUNA_INBOUND_API_KEY` em `DevOps-Cloud/docker-compose.yml` + `.env` + `.env.example`,
`kura-luna-ai/luna/.env.example`, e `EXPO_PUBLIC_LUNA_API_KEY` (o nome que o app já lia, só nunca
documentado) em `mobile-clinica-rn/.env.example` — os três com o mesmo valor default.

### 3. Identity generators desincronizados (achado do meu setup local — não é bug de produção)

Ao popular manualmente este Oracle local com o seed dev do Java (que insere `VETERINARIO`/`TUTOR`/
`PET`/`INVITE_TUTOR` com ID explícito), o gerador `GENERATED BY DEFAULT AS IDENTITY` dessas tabelas
nunca avança — a primeira inserção via .NET colide com o ID já ocupado (`ORA-00001` no PK). Resolvido
localmente com `ALTER TABLE x MODIFY id GENERATED BY DEFAULT AS IDENTITY (START WITH LIMIT VALUE)`.
**Isso não é um bug do projeto**: o fluxo real de deploy nunca roda esse seed dev contra Oracle
(`application-prod.yml` não inclui `db/callback`) — é um artefato específico de como bootei este
Oracle local para o smoke test. Documentado aqui só para quem for reproduzir o setup local.

## Triage HTTP na Luna — gap confirmado, sem impacto no app hoje

Ver D-6 do backlog original: a Luna **não tem** endpoint HTTP de submissão de triagem (`POST
/triage/analisar` citado em docs antigos nunca existiu como rota — triagem é heurística local via
CLI/webhook Twilio inbound, não IA/visão computacional neste momento, confirmado lendo
`src/ai/triage_engine.py`/`triage_rules.py` — sem import de torch/YOLO). Verificado nesta task:
`mobile-clinica-rn` **não tem nenhuma tela ou service que envie imagem/triagem para a Luna** —
`luna.tsx` só lê `getRelatorioTriagens` (relatório, .NET) e `getLunaHealth`. **Não é um gap real
hoje** — não há fluxo do app dependendo do endpoint ausente.
